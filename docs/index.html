Entitlement & Pricing Service

One governed service that resolves what a wealth client can access and what fee applies, from one versioned rule set, and returns the exact tier rule and fee schedule version that decided it.

What it demonstrates

A wealth platform asks two coupled questions in every client-facing app: what can this client tier access, and what fee applies. When each app keeps its own copy of the rules, the answers drift and no one can explain a past charge. This backend makes that logic one thing.

One resolve, one answer

A single endpoint reads the client, gathers the tier's entitlements, picks the fee rule, applies the minimum-fee floor, and returns the tier rule and schedule version that produced it.

Versioned pricing

Fee schedules are versioned, one published at a time. An admin drafts a new version (cloned from the live rules), edits it, and publishes it. A re-resolve returns the new fee under the new version.

An immutable audit

Every resolve writes a row that snapshots the entitlements, the fee, the firing rule id, and the schedule version. A later edit never changes a past row.

API-layer RBAC

Two roles enforced at the endpoint, read fresh from the staff table on every call. Middleware-style access control, not row-level security.

API surface

Service endpoints need an app-service or admin token. Admin endpoints need a pricing-admin token.

The screens

Resolve

Pick a client and a product, see the entitlements grid, the fee with its minimum-fee floor, and the exact tier rule and schedule version that fired.

Fee schedules

List every version, create a draft, edit its rules, and publish it. Editing a published version is refused.

Audit

The resolutions log, newest first. Open one to see its frozen snapshot, unchanged by later edits.

Governance

Switch role and run an access check that shows the API return 401, 403, and 200 for one admin endpoint.
